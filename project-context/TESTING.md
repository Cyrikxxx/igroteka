# Тестирование

**303 теста в 34 файлах** плюс **16 smoke-сценариев** на настоящих
сокет-соединениях.

Проверка перед коммитом — одна команда:

```bash
npm run check     # типы + линт + тесты
```

---

## Два набора в одном запуске

`vitest.config.ts` в корне описывает два проекта с разным окружением. Раздел
выбирается по расширению файла — это не соглашение на словах, а правило в
конфиге:

| Проект | Файлы | Окружение | О чём |
|---|---|---|---|
| `node` | `*.test.ts` (20 файлов) | node | серверная логика и чистые функции |
| `web` | `apps/web/tests/*.test.tsx` (12 файлов) | jsdom | хуки и экраны |

Запустить по отдельности:

```bash
npx vitest run --project node
npx vitest run --project web
```

### Node: логика без окружения

Сюда попадает всё, что можно проверить вызовом функции. Разыгрывание ночи,
подсчёт голосов, условия победы, состав ролей, очки и переход хода в Алиасе,
круг втроём, реплики ведущего, подпись куки, ключ для rate limit, видимость
истории.

Отдельно стоит `view.test.ts` — приватность в Мафии. Он проверяет
**сериализованный ответ**, а не типы: TypeScript спокойно пропустит лишнее поле
в объекте, который потом уйдёт в JSON, а тест на утечку роли — нет.

Такие тесты быстрые (весь набор — секунды), поэтому правил покрыто много.
Ради этого чистая логика и вынесена в `engine-core.ts` без Redis и сокетов
(см. [ENGINEERING.md §9](ENGINEERING.md)).

### Web: хуки и экраны

`@testing-library/react` в jsdom. Подменяются ровно две вещи:

- **сокет** — один модуль `lib/socket-client`, чтобы хук получал события, но не
  ходил в сеть;
- **навигация Next** — заглушка из `apps/web/tests/stubs`.

Есть отдельный тест на гидратацию: он ловит расхождение между серверной и
клиентской отрисовкой — ту самую ошибку, которая в разработке проявляется
предупреждением в консоли и легко проходит незамеченной.

> В выводе `npm test` виден один «error» из `use-hydrated.test.tsx`. Это
> намеренно: тест проверяет, что расхождение действительно ловится, и React
> печатает своё предупреждение. Все тесты при этом зелёные.

## Smoke-сценарии

Юнит-тесты не поймают то, что ломается **между** процессами: токен подписан не
тем секретом, событие называется иначе, чем ждёт клиент, комната не поднялась из
Redis. Проверять это руками — открывать шесть вкладок и играть партию целиком.

Smoke-скрипты делают то же самое программно: поднимают **настоящие** сокет-
соединения к запущенному серверу, ходят по REST за токенами, играют партию и
проверяют результат.

```bash
npm run dev                          # в одном терминале
npm run smoke:mafia -w @alias/ws     # в другом
```

| Сценарий | Что проверяет |
|---|---|
| `smoke:auth` | ws отвергает неавторизованные подключения и принимает корректные |
| `smoke:flow` | цепочка REST → токен → WS целиком |
| `smoke:lobby` | лобби Алиаса: создание команд, вход, переименование, рассылка |
| `smoke:game` | полный раунд Алиаса до записи результата |
| `smoke:trio` | круг из шести ходов втроём, локально |
| `smoke:trio-online` | то же онлайн: три места, старт только при всех троих |
| `smoke:rejoin` | возврат в комнату после выхода |
| `smoke:reconnect` | обрыв связи внутри фазы — состояние не теряется |
| `smoke:host` | передача комнаты и захват прав у пропавшего хоста |
| `smoke:host-spectator` | хостом может быть зритель; комната не зависает без игроков |
| `smoke:ingame` | подключение в идущую партию — попадаешь зрителем |
| `smoke:mafia` | партия Мафии на 6 клиентов: роли, ночь, утро, голосование, финал |
| `smoke:narrator` | режим ведущего: порядок шагов ночи и скрытые тайминги |
| `smoke:history` | итоги партии, доступ к ним и «убрать из своей истории» |
| `smoke:vote` | порядок фаз со знакомством и голосование за «никого не изгонять» |
| `smoke:cross-game` | код чужой игры во входе: отказ, и комната от этого не умирает |

Всем нужен запущенный `npm run dev` и поднятые базы.

### Два, которые стоит разобрать

**`smoke:narrator`** проверяет то, что руками не проверить вовсе. Он убеждается,
что шаг **мёртвой** роли всё равно случается и занимает заметное время. Без
этого смерть доктора была бы слышна раньше, чем о ней объявят: сайт просто не
позвал бы его ночью, и все за столом это заметили бы. Заодно проверяется отказ
ходить не в своё окно и то, что остаток шага скрыт от зала.

**`smoke:history`** создаёт две партии в одной комнате напрямую через Prisma —
доигрывать Мафию до победы скриптом долго и недетерминированно, а проверяется
здесь история, а не движок. Именно он поймал баг, из-за которого вторая партия
в комнате молча не сохранялась: `roomId` был объявлен уникальным, а ошибка
уникальности гасилась `.catch`.

## Наполнители комнат

Отдельно от smoke-сценариев: эти скрипты ничего не проверяют, а дают
**посмотреть глазами**. Вёрстка партии на пятерых и на шестнадцати выглядит
по-разному, а столько телефонов ради проверки экрана взять негде.

Скрипт подсаживает в вашу комнату живых сокет-клиентов, и дальше они играют
сами — вы остаётесь обычным игроком и смотрите со своего экрана. Цели и слова
боты выбирают наугад: партия должна двигаться, а не выигрываться.

| Скрипт | Комната |
|---|---|
| `mafia:fill` | Мафия, до 16 игроков |
| `alias:fill` | Алиас онлайн, до 36 игроков |

**Мафия.** Создайте комнату в браузере, останьтесь в лобби и запустите:

```bash
npm run mafia:fill -w @alias/ws -- K7F2QD 16
```

Второй аргумент — сколько игроков должно быть за столом **всего, считая вас**.
Боты займут места, вы жмёте «Начать». Дальше они подтверждают роль, ходят
ночью и голосуют днём.

**Алиас.** Команды заводит только хост, поэтому создайте их в лобби сами —
боты займут свободные места и рассядутся по командам поровну:

```bash
npm run alias:fill -w @alias/ws -- K7F2QD 12
```

Мест не хватило — скрипт скажет, сколько ещё нужно, и посадит сколько влезет.
Когда очередь объяснять доходит до бота, он отвечает на слова и подтверждает
итог раунда, чтобы круг шёл дальше.

Обоим нужен запущенный `npm run dev`. Боты живут, пока скрипт не остановлен;
`Ctrl+C` — все выходят из комнаты.

## Чего тесты не покрывают

Честнее назвать, чем делать вид:

- **вёрстку и адаптивность** — headless-браузера в проекте нет, скриншотных
  тестов тоже. Раскладка проверяется глазами;
- **синтез речи** — `speechSynthesis` в jsdom отсутствует. Логика выбора голоса
  и дедупликации реплик покрыта, само произношение — нет;
- **Docker и деплой** — `deploy.sh` и compose-файлы не проверяются
  автоматически;
- **нагрузку** — сколько комнат выдержит один инстанс ws, никто не мерил.
